# Feature Specification: Codec Version Strategies

**Feature Branch**: `refactor/core-versioned-codec-seam`

**Base**: `develop` — after PR #61 (feature 002 follow-up) merges

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "Refactor MyencCodec into a version-dispatching façade with per-version strategy objects (v1 extracted as _V1Strategy), totality invariant, pre-refactor compatibility fixtures, rewrap round-trip guard."

## Overview

Feature 002 gave the project a single authority that answers "which versions exist". Header
handling did not follow: `MyencCodec` still hardcodes **one** layout. It reads the magic, gates
on the registry, then parses v1's fields inline — so every future version must be spliced into
that one function, and "the structure for this version" has no place to live.

This feature restructures header handling so each registry version owns its layout in a
**strategy object**, dispatched by a public façade whose signature never changes. The registry
stays exactly where it is: pure version authority, no byte offsets, no parsing.

Two properties define success, and both are pinned by committed artifacts, not code review:

1. **Neutrality.** No byte of v1 behaviour moves. Files encrypted before the refactor decrypt
   exactly as before; the same header inputs encode to the same bytes. Proven by corpora
   generated with the pre-refactor code, which must pass **unedited** afterwards.
2. **Machinery.** A new version slots in as one strategy plus one registry row — and forgetting
   the strategy is a red test (the totality invariant), not a runtime failure on a user's file.

### Why this stands alone / why now

The extraction has a clean proof only while exactly one version exists: the freeze guard and the
golden vectors pass untouched after a pure move, and *that* is the proof the move leaked nothing.
Deferring the machinery to the first new version means that PR mixes mechanical extraction with
new layout logic — the two changes become un-auditable as one. Doing it now, at one version, the
v2 PR is purely additive: a strategy file and its tests.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Files encrypted before the refactor decrypt exactly as before (Priority: P1)

Someone has `.latch` files made by the current app. They update to the build containing this
refactor. Every file still decrypts to the same plaintext, with the same failures for wrong
passphrases and tampered files.

**Why this priority**: This is the user-facing safety property of a refactor of shipped decode
behaviour. Any behavioural difference from the base is not this feature — it is a bug.

**Acceptance**: A committed corpus of raw files (empty, 1 byte, small, larger than one chunk so
the multi-chunk tag path is exercised, binary content) with `.latch` fixtures encrypted by the
pre-refactor code and a manifest of plaintext hashes. After the refactor, every fixture decrypts
and its plaintext hash matches the manifest. Two negative fixtures hold as well: a wrong
passphrase fails fast at the key wrap, before the body is touched; a tampered body (one flipped
byte) fails at a chunk tag and never emits partial plaintext.

### User Story 2 - The same header inputs produce the same bytes (Priority: P1)

Header encode/decode are pure functions: a header in, bytes out — no randomness. The refactor
must be byte-identical at exactly this layer, because this is the layer it moves.

**Why this priority**: Alongside Story 1, this is the neutrality proof. The full-file corpus
passes through crypto adapters with per-file randomness; the header corpus is the deterministic
pin on the refactored code itself.

**Acceptance**: A header corpus covering the shape matrix (zero/one/multiple wraps,
encrypted-filename present and absent, boundary chunk sizes, flag variants) with the encoded
hex generated by the pre-refactor code. After the refactor, the same `FileHeader` encodes to
byte-identical output.

### User Story 3 - A future version cannot be added incompletely (Priority: P1)

A maintainer adds a version row to the registry. Until the version also has a parsing/encoding
strategy, the test suite is red.

**Why this priority**: This is the machinery property the whole feature exists to provide:
fail-closed is guaranteed structurally, not by convention.

**Acceptance**: A totality test asserts the dispatch table covers the registry exactly. Adding
a row without a strategy fails that test; adding a strategy without a row is equally visible.
No code path can reach a user's file with a version the parser cannot handle.

### User Story 4 - Rewrap preserves version identity (Priority: P2)

Changing a passphrase or adding a recipient re-encodes the header. Whatever version the original
container had, the re-encoded container has the same version byte and the same version-specific
fields.

**Why this priority**: The envelope pass-through paths re-emit `hdr.version` unchanged; the
re-encode must go through the façade dispatch, never a hardcoded v1 encoder. This is the failure
mode the architecture exists to prevent, so it gets its own guard.

**Acceptance**: A round-trip test: parse a header, re-encode through the public entry point,
and assert the version byte and version-specific fields are byte-identical.

### Edge Cases

- Headers truncated at every prefix, per version — fail closed with the same typed error.
- Unknown version byte — refused by the registry gate, never guessed at.
- Wrap count of zero, one, and multiple; unknown wrap type.
- Encrypted-filename field present vs absent.
- Multi-chunk files (body larger than one chunk) and empty files.
- Version-specific fields surviving a rewrap round-trip.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A single public entry point handles the version-independent prefix: minimum
  length check, magic verification, version byte read, registry gate (`require`). Its
  signature and error semantics are unchanged from the base.
- **FR-002**: Every version in `FormatVersionRegistry.all` has exactly one strategy owning
  the parse and encode of that version's layout — from the first version-specific byte onward.
- **FR-003**: Totality is enforced by a test: the dispatch table's key set equals the
  registry's entry set. A registry row without a strategy, or a strategy without a row, is a
  failing test.
- **FR-004**: The strategy contract is `decode(bytes, offset) -> (FileHeader, consumed)` and
  `encode(FileHeader) -> bytes`. Strategies are pure: no randomness, no I/O, no platform
  dependencies — they live in `myenc_core`.
- **FR-005**: Encoding determinism is pinned by the pre-refactor header corpus: identical
  `FileHeader` input produces byte-identical output before and after the refactor.
- **FR-006**: The pre-refactor full-file compatibility corpus decrypts to plaintext whose
  hash matches the manifest.
- **FR-007**: Negative fixtures hold: wrong passphrase fails fast at the key wrap (before
  the body is touched); a tampered body fails at a chunk tag with no partial plaintext
  emitted. This is the project's non-negotiable wrong-passphrase vs corrupt-file distinction,
  pinned on pre-refactor bytes.
- **FR-008**: A rewrap round-trip test pins that parse → re-encode preserves the version
  byte and version-specific fields byte-for-byte.
- **FR-009**: v1 error semantics are frozen: the same inputs produce the same typed errors.
  The freeze guard (`codec_freeze_test.dart`) and the golden vectors pass **unedited** — any
  edit to them means the refactor leaked behaviour and is reverted, not fixed.
- **FR-010**: The `FileHeader` data model remains a superset: fields that exist in a future
  version but not v1 are optional, and consumers check capabilities (BL-001), not version
  numbers, before touching them.
- **FR-011**: The registry remains pure version authority: no byte offsets, no layout
  knowledge, no parsing. When capability fields land (BL-001 / issue #62), they ride on the
  `FormatVersion` entries that already key the dispatch — the dispatch itself does not move.
- **FR-012**: v1's exhaustive battery — round-trips, per-field corruption cases, every-prefix
  truncation sweep, single-byte mutation sweep, random-garbage property tests — is attached
  to v1's strategy explicitly, satisfying BL-004's per-version test matrix for v1.

### Key Entities

- **FormatVersionStrategy** — the per-version contract (`decode` / `encode`); one
  implementation per registry entry.
- **MyencCodec façade** — the unchanged public entry point: sanity + magic + gate +
  dispatch; the only code that answers "which strategy?".
- **V1 strategy** — today's decode/encode body moved verbatim; owns v1's tables, bounds,
  and error conditions.
- **Header corpus** — committed encoded-hex fixtures across the v1 shape matrix.
- **Compatibility corpus** — committed `.latch` fixtures + raw files + hash manifest,
  generated by pre-refactor code.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of compatibility-corpus fixtures decrypt with plaintext hash equal to
  the manifest entry — zero mismatches.
- **SC-002**: 100% of header-corpus fixtures encode byte-identically after the refactor —
  zero byte differences.
- **SC-003**: The freeze guard and golden vectors pass with zero edits across the entire
  change set.
- **SC-004**: The totality test is red exactly when the registry and the strategy table
  disagree — demonstrated at least once in review by temporarily removing a strategy.
- **SC-005**: Test counts never drop below the pre-change baseline (core 86, adapters 36,
  app 143); the new suites add to them.
- **SC-006**: The diff contains no behavioural change to decode/encode logic — reviewable
  as pure moves plus additive machinery, in separate commits.

## Assumptions

- Exactly one format version exists at the time of this work; v2 arrives with
  `001-folder-encryption`, which will consume the machinery.
- The superset `FileHeader` model remains viable (precedent: `encryptedFilename`); a sealed
  hierarchy is the escape hatch and is out of scope here.
- Capability fields (BL-001) and registry-held layout schemas (BL-002 option b) stay out of
  scope; this feature builds the seam they will plug into.

## Dependencies

- PR #59 (central format-version registry) — merged, present on `develop`.
- PR #61 (remove `FileHeader.supportedVersion` alias) — must merge first; this feature
  branches off `develop` after it.
- `sodium` native assets for the crypto-backed corpora tests — existing flow, no change.

## Downstream Consumers

- **`001-folder-encryption`**: drops its interim version constants, adds one registry row and
  one strategy, ships the BL-004 battery for v2. Its PR becomes purely additive.
- **Envelope service** (`changePassphrase` / `addRecipient`): re-encode through the façade
  dispatch (FR-008 guard).
- **BL-001 capability checks**: key off the same `FormatVersion` entries that key the
  dispatch; no further restructuring needed.

## Out of Scope

- Capability fields on `FormatVersion` (BL-001, issue #62).
- Registry-driven layout schemas / the registry as parser (BL-002 option b).
- A sealed `FileHeader` hierarchy.
- Any change to the adapters, the body encryption path, or any `.latch` byte.
- Adding any new format version — this feature ships the machinery and v1 only.
